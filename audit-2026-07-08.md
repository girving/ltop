## Confirmed correctness findings

### [CRITICAL] src/syscall.rs:395 — Darwin BSD syscall asm wrappers do not declare the kernel's x1 clobber — inline-asm UB on every mac syscall

*subsystem: mac-sys, panel votes: CCC*

**Claim:** xnu's arm64 BSD syscall return path (bsd/dev/arm/systemcalls.c, arm_prepare_u64_syscall_return) writes user x1 on every return: error path sets `ss64->x[0]=error; ss64->x[1]=0` and success sets `x[1]=uu_rval[1]` for _SYSCALL_RET_INT_T/UINT_T and `x[1]=0` for OFF_T/ADDR_T/SIZE_T/SSIZE_T/UINT64_T (verified against apple-oss-distributions/xnu). The darwin::aarch64 wrappers (src/syscall.rs:395-479) declare x1 either not at all (`syscall1`, lines 395-408 — used for close/getpid/exit) or as input-only `in("x1") a2` (`syscall2/3/4/6`, lines 411-479 — used for read/write/open/ioctl/madvise/gettimeofday/sysctl/proc_info). Rust's inline-asm rules make it undefined behavior for asm code (including the kernel acting through `svc`) to modify a register that is not an output/clobber: the compiler is entitled to assume x1 still holds its pre-syscall value (e.g. a live buffer pointer) after the block. Mach traps are unaffected (osfmk/arm64/sleh.c writes only x[0]), so only the BSD wrappers need `lateout("x1") _` / `inlateout("x1") a2 => _`.

**Failure scenario:** Production macOS build (opt-z + LTO, wrappers fully inlined): LLVM keeps a value live in x1 across the `svc #0x80` — e.g. the slice base pointer in tty::write_stdout's partial-write loop or platform code that reuses a length/pointer after a read/write call. The kernel overwrites x1 with 0 (or uu_rval[1]) on syscall return; the compiler-cached value is silently corrupted, yielding a wrong pointer/length in subsequent code — anything from EFAULT'd writes (dropped frames) to reads through a corrupted pointer. Currently latent (register allocation happens to reload x1), but any rustc/LLVM upgrade or code motion can surface it; it is a contract violation on every Darwin BSD syscall the monitor issues each tick.

### [CRITICAL] src/gpu/agx.rs:169 — OSBIN_OBJS_CAP=1024 is smaller than the real AGXAccelerator property blob (~2057 items), so OsBinary::parse fails every tick and GPU used-memory is silently reported as 0

*subsystem: osbinary, panel votes: CCC*

**Claim:** OsBinary::parse (src/osbinary.rs:116-125) returns None when append() exhausts objs_buf (src/osbinary.rs:324-330), and the caller in populate (src/gpu/agx.rs:186-194) treats that as 'no data', leaving total_used_mib at 0 while still reporting totals (iokit_ok is set unconditionally after the loop, src/gpu/agx.rs:220). The doc comment on parse (src/osbinary.rs:111-114) and the sizing comment at src/gpu/agx.rs:165-168 justify 1024 entries by counting only the root dict's ~80 keys, but objsArray entries are one per emitted item (every nested dict/array/number/symbol-first-occurrence — verified against xnu OSUnserializeBinary, which appends every non-ref object via setAtIndex(objs, objsIdx, o)). Measured on the host M2 via `ioreg -a -r -c AGXAccelerator -d 1`: the property table serializes to ~2057 objs entries, dominated by the standard IOReporting property IOReportLegend (~1902 entries), which is present on every AGXAccelerator. 2057 > 1024, so the accelerator-root parse fails unconditionally on real hardware.

**Failure scenario:** Verified end-to-end on this machine: the kernel reports PerformanceStatistics['In use system memory'] = 1,007,894,528 bytes (~961 MiB), but `target/release/ltop --once` renders the header as 'gpu: 0%  0.0G active'. Every tick on any Apple Silicon Mac: io_registry_entry_get_properties_bin returns the AGXAccelerator blob, parse overflows the 1024-entry objs buffer at ~item 1024 of ~2057, read_agx_used_mib_blob never runs, and the GPU active-memory figure is permanently 0.0G. Per-PID GPU% still works (AGXDeviceUserClient blobs are small), making the wrong output easy to miss. Test coverage masks it: parses_real_agx_properties uses a 4096-entry buffer (src/osbinary.rs:615) and agx_init_and_first_tick (src/gpu/agx.rs:525) never asserts used_mib > 0.

### [HIGH] src/main.rs:1391 — Unbounded /proc/<pid>/cmdline read into the 512 KB arena aborts ltop on large-but-legal command lines (arena overflow assert)

*subsystem: arena, panel votes: CCC*

**Claim:** The Linux collect path reads the entire cmdline into an arena FStr with no size cap: `inner.str("cmdline", |b| { ... loop { let n = syscall::read_buf(fd, chunk); ... b.extend_from_slice(&chunk[..n as usize]); ... } })` (src/main.rs:1391-1404). Every `extend_from_slice` goes through `arena::bump`, which hard-asserts `(end as usize) <= SIZE` with SIZE = 512 KB (src/arena.rs:306-310, src/arena.rs:228). Linux permits total argv+envp up to RLIMIT_STACK/4 (typically ~2 MB with an 8 MB stack; kernel fs/exec.c bprm limit), so a monitored process can legally have a cmdline far larger than the arena's remaining space (~300-400 KB after cross-tick and per-tick allocations). The macOS path is capped (MACOS_ARG_MAX blob sizing at src/main.rs:1116-1120); the Linux path has no equivalent cap.

**Failure scenario:** ltop's stated primary use is monitoring C++ builds. A linker or compiler invocation with a few-hundred-KB command line (thousands of .o paths — routine in large builds) has high RSS, so `may_qualify` is true and the cmdline is read; the arena bump assert fires (`arena overflow: need N bytes...`) and, with panic=immediate-abort, the monitor aborts mid-run.

### [HIGH] src/main.rs:1127 — macOS args slice includes exec_path at index 0, breaking display logic that assumes Linux argv layout (interpreter processes show the interpreter, not the script)

*subsystem: main, panel votes: CCC*

**Claim:** macos_proc_args_into (main.rs:1184-1215) fills out[0]=exec_path, out[1]=argv[0], ... (its own doc comment: "fill out with [exec_path, argv0, ...]"; xnu's KERN_PROCARGS2 blob is [argc][exec_path\0][pad][argv0\0]...). This slice is passed unchanged to build_display_into/find_script_arg (main.rs:1138), but on Linux args[0] is argv[0] (cmdline NUL-split, main.rs:1411). find_script_arg (main.rs:1699-1712) does args.iter().skip(1) assuming it skips exactly the interpreter; on macOS skip(1) skips only exec_path, so the first candidate examined is argv[0] itself (e.g. "python3"), which doesn't start with '-' and is returned as the "script". is_lean_related's args.iter().take(3) window (main.rs:1686) is likewise shifted by one. CLAUDE.md explicitly requires the two collect_procs paths to stay semantically in sync.

**Failure scenario:** On macOS, run `python3 train.py` (or any node/ruby/perl process) hot enough to display: args = ["/opt/homebrew/.../python3.12", "python3", "train.py"]; is_interpreter(basename(args[0])) matches, find_script_arg returns basename(args[1]) = "python3", so the COMMAND column shows "python3" instead of "train.py". Same binary logic on Linux correctly shows "train.py".

### [HIGH] src/main.rs:548 — page_size hardcoded to 4096 makes RSS silently wrong by 4x/16x on 16K/64K-page aarch64 Linux kernels

*subsystem: main, panel votes: CCC*

**Claim:** run() sets `let page_size: u64 = 4096;` with a comment justifying it only for x86_64, but the project ships and CI-builds a static-linux-aarch64 target (.cargo/static-linux-aarch64.json). ### [HIGH] src/syscall.rs:411 — Darwin aarch64 syscall wrappers do not declare x1 as clobbered, but xnu writes x1 on every successful int-returning syscall (asm! contract violation / potential miscompilation)

*subsystem: linux-sys, panel votes: CCC*

**Claim:** All six darwin::aarch64 wrappers (syscall1..syscall6, src/syscall.rs:396-479) declare argument registers as plain `in("x1")..in("x5")` (or omit x1 entirely in syscall1), which per Rust asm! semantics promises the asm block leaves those registers unchanged. But xnu's arm64 BSD syscall return path clobbers x1: apple-oss-distributions/xnu bsd/dev/arm/systemcalls.c, arm_prepare_u64_syscall_return, contains `case _SYSCALL_RET_INT_T: ss64->x[0] = uthread->uu_rval[0]; ss64->x[1] = uthread->uu_rval[1]; break;` (verified against the primary source). open/openat/close/ioctl/getpid/madvise/gettimeofday/sysctl/proc_info are all _SYSCALL_RET_INT_T, so on every successful call the kernel overwrites x1 with uu_rval[1] while the compiler is entitled to assume x1 still holds the second argument. The adjacent Linux aarch64 comment (src/syscall.rs:246-250) claims `in(...)` gives lateout/clobber semantics — that is incorrect (it is harmless on Linux only because the Linux arm64 kernel restores x1..x7 from pt_regs).

**Failure scenario:** On the macOS production build, any call site where LLVM keeps a live value in x1 across an inlined syscall (e.g. a buffer pointer reused after `close`/`ioctl` in a loop at opt-level=z) reads a stale register whose contents the kernel replaced with uu_rval[1] (typically 0). This is UB by the asm! contract; concrete manifestation is register-allocation-dependent and can appear or move with any compiler upgrade or unrelated code change, producing wild pointer dereferences or silently wrong values. Fix is to mark x1 (and conservatively x2..x5, matching what libsyscall's function-call boundary implicitly clobbers) as `lateout(...) _` or `inlateout`.

### [HIGH] src/sandbox.rs:214 — restart_syscall missing from seccomp allowlist: SIGSTOP/SIGCONT (e.g. Ctrl-Z + fg) during the tick nanosleep kills ltop with SECCOMP_RET_KILL_PROCESS

*subsystem: sandbox, panel votes: CCC*

**Claim:** The 'Notably absent: restart_syscall' comment (src/sandbox.rs:214-218) claims the kernel only invokes restart_syscall 'when a syscall is interrupted by a signal whose handler returned with SA_RESTART'. This is backwards. Verified against arch/arm64/kernel/signal.c (v6.9): when get_signal() returns false (NO handler runs — exactly the stop-signal/SIGCONT case), the kernel executes `if (retval == -ERESTART_RESTARTBLOCK) setup_restart_syscall(regs);` which sets `regs->regs[8] = __NR_restart_syscall` (128 on aarch64 per include/uapi/asm-generic/unistd.h; 219 on x86_64 per syscall_64.tbl); the handler-present case instead converts ERESTART_RESTARTBLOCK to -EINTR. ltop installs no signal handlers, so the no-handler restart path is the one that fires. nanosleep returns -ERESTART_RESTARTBLOCK, restart_syscall enters through the normal syscall path and IS evaluated by the seccomp filter, and neither ALLOW_DIRECT array (src/sandbox.rs:220-231 x86_64, 259-270 aarch64) contains 219/128, so the filter returns DENY_ACTION = SECCOMP_RET_KILL_PROCESS. Note CLAUDE.md's own description of the filter lists restart_syscall in the allowlist — the code has diverged from that spec. tests/sandbox_smoke.rs cannot catch this: it only checks `Seccomp: 2` in /proc/thread-self/status and never sleeps under the filter or exercises a stop/continue.

**Failure scenario:** Run the production min build (cfg(libc_free), sandbox installed). The tick loop spends ~98% of wall time in platform::sleep -> nanosleep (50 ms poll steps). User presses Ctrl-Z (SIGTSTP) and later `fg`/`bg` (SIGCONT), or any session manager/debugger sends SIGSTOP+SIGCONT. On resume, the kernel rewinds the PC and substitutes nr = restart_syscall; seccomp evaluates nr 219/128, finds no match, and kills the entire process (SIGSYS, KILL_PROCESS). ltop dies instantly on resume, leaving the terminal in raw mode with the cursor hidden (the tty-restore guard never runs).

### [HIGH] src/gpu/rm.rs:392 — GPU device paths derived from a contiguous loop index instead of the driver-reported minor number, breaking monitoring when any GPU is excluded

*subsystem: gpu, panel votes: CCC*

**Claim:** count_attached_gpus (rm.rs:432-454) issues NV_ESC_CARD_INFO and returns only the count of valid entries (`cards.iter().filter(|c| c.valid != 0).count()`), discarding the rest of each NvIoctlCardInfo -- including its `minor_number: u32` field (rm.rs:134) that the ioctl reply actually populates. try_init's per-GPU loop (rm.rs:390-405) then opens `/dev/nvidia{i}` for `i in 0..n_gpus`, assuming the N valid GPUs occupy minors 0..N-1 contiguously. Per NVIDIA's driver source (kernel-open/nvidia/nv.c `nvidia_read_card_info`), the CARD_INFO reply is a compacted list: `for (nvl = nv_linux_devices; ...) { if (nv->flags & NV_FLAG_EXCLUDE) continue; ci[i].valid = NV_TRUE; ci[i].minor_number = nvl->minor_num; i++; }` -- excluded GPUs are skipped from the compacted array, but the real minor numbers of the remaining entries are NOT renumbered to close the gap. Minor numbers are assigned to every detected GPU in probe order via `nv_linux_assign_minor_locked` (a shared bitmap, `find_first_zero_bit`), independent of exclusion, and `nv_open_device` explicitly returns -EPERM for an excluded GPU's device node. So a documented, standard driver configuration (`NVreg_ExcludedGpus`, used for VFIO passthrough or reserving a display-only card) produces non-contiguous minors among the valid GPUs, e.g. valid GPUs at minors {0, 2} with minor 1 excluded.

**Failure scenario:** Host has 3 GPUs; minor 1 is excluded via NVreg_ExcludedGpus, leaving valid GPUs at minors 0 and 2. CARD_INFO reports 2 valid entries. ltop computes n_gpus=2 and opens /dev/nvidia0 (succeeds, correct GPU) then /dev/nvidia1 (the excluded GPU's node) instead of /dev/nvidia2. Opening the excluded node fails at the open(2) syscall (driver returns -EPERM from nv_open_device), so `open_rw(fd_path)?` returns None and the `?` aborts try_init entirely -- all GPU stats silently disappear (falls back to the empty/no-GPU State) even though 2 perfectly usable GPUs exist. The fix is to read and use each entry's `minor_number` field from the CARD_INFO array instead of resynthesizing indices 0..n_gpus.

### [HIGH] src/tty.rs:100 — Raw mode leaves ISIG enabled with no signal handler anywhere in the codebase, so Ctrl-C (SIGINT) kills the process without restoring the terminal

*subsystem: util, panel votes: CCC*

**Claim:** `enter_raw_mode` only clears `ICANON | ECHO` in `c_lflag` (src/tty.rs:100); it never clears `ISIG` (Linux 0o0000001 / macOS 0x80), so the terminal driver still generates SIGINT on Ctrl-C. The whole codebase (grepped src/*.rs) installs no `sigaction`/`rt_sigaction` for SIGINT/SIGTERM anywhere outside the Linux `sandbox-trap` feature's SIGSYS-only handler (src/sandbox.rs), and there is no `no_std` runtime signal setup. Default disposition for SIGINT is `Term`, which tears the process down via the kernel with no Rust unwinding/Drop execution, so `RawModeGuard::drop` (src/tty.rs:112-118), which restores `orig` termios and re-shows the cursor (`\x1b[?25h`), never runs.

**Failure scenario:** Empirically verified with a pty harness: launched `target/release/ltop` under a pty, confirmed real rendered frames, then sent SIGINT to the pid. `waitpid` shows the process terminates via signal 2 (SIGINT) as expected, but comparing `termios.tcgetattr` on the pty master before and after exit shows ICANON and ECHO remain off (`lflag` unchanged: `0b10011000011` both before and after). The user's shell is left with a non-canonical, no-echo terminal and a hidden cursor after pressing Ctrl-C to quit ltop (a very common exit gesture for a top-like tool, and not disabled/blocked anywhere), requiring a manual `reset`/`stty sane` to recover. The only documented quit key is `q` (README.md:101); Ctrl-C is not handled at all.

### [MEDIUM] src/arena.rs:446 — uncommit_tail hardcodes 4096-byte pages; on 16K/64K-page aarch64 Linux kernels madvise either silently fails or MADV_DONTNEEDs past the arena, zeroing ARENA.offset

*subsystem: arena, panel votes: CCC*

**Claim:** Linux `uncommit_tail` uses `const PAGE_SIZE: usize = 4096` (src/arena.rs:446) to compute `tail_start` and a 4K-multiple `len`, then calls `madvise(tail_start, len, MADV_DONTNEED)` (src/arena.rs:462). The project ships an aarch64 static target (.cargo/static-linux-aarch64.json); aarch64 kernels commonly use 16K (Asahi) or 64K (RHEL-alt) pages. Verified against kernel v6.9 mm/madvise.c `do_madvise`: `if (!PAGE_ALIGNED(start)) return -EINVAL; len = PAGE_ALIGN(len_in);` — start must be aligned to the KERNEL page size and len is rounded UP to a kernel-page multiple. So on a 16K kernel: (a) if the 4K-rounded tail_start is not 16K-aligned, madvise returns EINVAL every tick (return value ignored) and no RSS is ever reclaimed; (b) if tail_start happens to be 16K-aligned, PAGE_ALIGN rounds len up by up to 12 KB past `arena_end`, and MADV_DONTNEED zero-fills the page containing `Storage.offset` — which repr(C) places immediately after `buf`, i.e. at exactly arena_end (src/arena.rs:246-254) — plus any following statics.

**Failure scenario:** On Asahi Linux (16K pages) with the link-time base/offset alignment landing on case (b): after the first tick, `uncommit_tail` zeroes ARENA.offset; the next tick's `replace2` hard assert `old2_end == ARENA.offset.get()` (src/arena.rs:807) fires and the monitor aborts — or, if allocations occur first, they start at offset 0 and overwrite the live cross-tick prev/gpu_prev spans (aliasing mutable views of the same bytes). Case (a) is a silent per-tick reclaim failure (RSS never returned to the kernel).

*subsystem: arena, panel votes: CC*

### [MEDIUM] src/arena.rs:703 — replace/replace2/compact build closures receive the same-'id Frame: FSpans allocated inside can be stashed past the rewind, yielding two live &mut to the same arena bytes from safe code

*subsystem: arena, panel votes: CRC*

**Claim:** `Frame::replace` (src/arena.rs:703), `replace2` (787), and `compact` (883) pass the build closure `&mut Frame<'id>` with the caller's brand (unlike `Frame::scope`, which mints a fresh 'sub brand). Any FSpan/FBox the closure allocates is branded 'id and can be moved into a captured `Option<FSpan<'id, T>>` outside the closure. After `build` returns, these methods rewind `ARENA.offset` below the stashed span's bytes (e.g. src/arena.rs:743, 851, 910) and later allocations reuse them. Additionally, the closure may return a pre-existing lower span; the only guards are `debug_assert!(new_span.offset > old_start)` (727) / `debug_assert!(result.offset >= dst)` (891), compiled out of release builds, after which `copy_down` runs with dst > src — violating its precondition and producing a corrupt copy.

**Failure scenario:** Safe code: `let mut stash = None; let next = f.replace("r", prev, |fr, _| { stash = Some(fr.collect("s", 0u32..8)); fr.collect("n", 0u32..1) });` — replace rewinds to old_start+4; `f.vec::<u32>("v", 8)` then hands out the same bytes; `stash.as_mut_slice()` and the FVec are two simultaneously live &mut over identical memory (UB), and stash's Drop later runs drop_in_place over reused bytes. Current callers (main.rs run loop, gpu backends) obey the convention, so this is a latent soundness hole in the arena's central safety claim rather than a live bug.

**Dissenting vote:** I confirmed the type-level claim is real: replace/replace2/compact hand the build closure &mut Frame<'id> with the *same* 'id as the caller (not a fresh 'sub brand like Frame::scope mints), so a closure that captures an outer `let mut stash: Option<FSpan<'id, T>>` can smuggle an arena allocation past the method's rewind. I wrote and ran the exact repro (tests/repro_stash.rs, `cargo test --release`) and it compiled under safe code and printed corrupted overlapping data (`stash = [3, 4, 5, 6, 7, 5, 6, 7]` after a later `f.vec` allocation reused the same bytes), confirming the mechanism works as described. However, the review lens is triggerability in the shipped production binary: grepping every actual call site (src/main.rs:601 replace2, src/main.rs:191/1109/1389 compact, src/gpu/agx.rs:160/241, src/gpu/rm.rs:583) shows every current closure that "crosses the closure boundary via &mut captures" (the codebase's own documented idiom, e.g. main.rs:1104 comment) only ever captures plain scalars (bool, u64) — never an FSpan/FBox/FVec. No caller in main.rs's run loop or either GPU backend stashes an arena handle out of a replace/replace2/compact closure; the unsound pattern exists only as an API-contract gap, not as executed code. Exploiting it requires writing new caller code that doesn't exist anywhere in the tree — not a specific kernel input, race, or cfg branch — so there is no concrete execution path in any current production configuration (Linux libc_free min build, mac min build, or the glibc test build's real call sites) that reaches this. It should be refiled as a lower-severity API-hardening note (mint a fresh sub-brand for these three closures the way scope does, or add a compile_fail test documenting the gap) rather than a medium "live soundness hole in shipped ltop" finding.

### [MEDIUM] src/arena.rs:1378 — FVec::retain_in_place double-drops elements if the keep closure panics (test builds unwind)

*subsystem: arena, panel votes: CRC*

**Claim:** `retain_in_place` (src/arena.rs:1378-1400) drops discarded elements (`ptr::drop_in_place(self.slot_ptr(r))`, 1396) and moves kept elements down (`ptr::copy_nonoverlapping`, 1390) as it iterates, but only assigns `self.len = w` after the loop completes (1399). If `keep` panics mid-loop, `self.len` is still the original length; during unwinding, `FVec::drop` → `clear()` → `truncate(0)` (1526-1530, 1406-1412) runs `drop_in_place` on every slot in 0..old_len, including slots already dropped (discards) and moved-from source slots — a double drop. std's Vec::retain uses a drop guard (BackshiftOnDrop) for exactly this; there is none here.

**Failure scenario:** Under `cargo test` (std + unwinding, where per CLAUDE.md the arena Drop paths are load-bearing): a test exercising `filter_with_children`'s retain over FVec<ProcInfo> (whose FSmallStr display has a real Drop) with a closure that panics after at least one element was discarded or shifted → double drop_in_place = UB in the test process. Production (panic=abort) is unaffected.

**Dissenting vote:** The bug claim is real at the code level: retain_in_place (arena.rs:1378-1400) assigns self.len = w only after the loop, and if the `keep` closure panics mid-loop, an unwind would run FVec::Drop -> clear() -> truncate(0), which drop_in_places every slot in 0..old_len via self.len — re-dropping already-discarded slots and moved-from source slots. That part of the analysis is accurate.

But triggerability fails for production. Cargo.toml sets `panic = "abort"` on both [profile.release] and [profile.min], and the min profile additionally sets `-Cpanic=immediate-abort` (killing even the unwind machinery/backtrace stack, per CLAUDE.md lesson 4/6). Production is also `#![cfg_attr(not(test), no_std)]`, single-threaded, no_std/no_main. Under any of these configurations, a panic inside the `keep` closure terminates the process immediately — there is no stack unwinding, so `Drop::drop` for the FVec is never invoked and the double-drop path the finding describes cannot execute. The finding's own failure scenario explicitly requires "cargo test (std + unwinding)" and explicitly concedes "Production (panic=abort) is unaffected."

Cargo's test harness is the one place unwinding survives: Cargo documents that test/bench/build-script/proc-macro targets always compile with panic=unwind regardless of the profile's `panic` setting (absent the nightly-only `-Z panic-abort-tests`), which is why CLAUDE.md itself notes "ScopeGuard::drop and FReserve::drop unwind paths are elided in production (panic=abort); they're load-bearing under cargo test (std + unwinding)." So the only place this UB could fire is inside `cargo test`, and even there, no current test's `keep` closure panics — the sole production call site (src/main.rs:967, `procs.retain_in_place`) is a straight-line closure with no `unwrap`/indexing that isn't structurally guaranteed by the "next pushed in lockstep with procs" invariant, so it would need a second, independent bug (index mismatch) to even panic in the first place.

This matches the explicit refutation criterion: a bug that is only reachable in test builds (std+unwind), never in the shipping no_std/panic=abort/immediate-abort binary on any platform, is refuted as filed at medium severity. It could legitimately be refiled at low severity as a test-harness hardening item (add a drop guard so a panicking `keep` during `cargo test` doesn't double-drop), but it is not a medium-severity production defect.

### [MEDIUM] src/main.rs:274 — PID reuse across ticks yields enormous bogus CPU% via wrapping_sub of unrelated cumulative counters

*subsystem: main, panel votes: CCC*

**Claim:** compute_cpu matches prev solely by pid: `prev.get(&pid)` then `new_bits.wrapping_sub(p.cpu_bits()) & CPU_MASK`. There is no process-identity check (e.g. starttime, as top/htop use). If a pid is reused between ticks, the new process's small cumulative counter minus the dead process's large counter wraps in the 31-bit domain to a delta near 2^31, producing CPU% in the billions. **Failure scenario:** The concrete high-severity defect above (restart_syscall → KILL_PROCESS on SIGSTOP/SIGCONT) passes the entire test suite: the interpreter tests never generate nr=219/128 and the smoke test child never sleeps or gets stopped. Any future tick-loop syscall addition that forgets the allowlist likewise passes CI and dies only in production use.

### [LOW] src/sort.rs:65 — sort_by_u32_key's "u32 key at byte offset 0" precondition is enforced only by doc convention for non-#[repr(C)] tuple types, not by the type system

*subsystem: util, panel votes: C*

**Claim:** `sort_by_u32_key<T>`'s const-asserts (src/sort.rs:63-66) only check `size_of::<T>() % 4 == 0` and `align_of::<T>() >= 4`; nothing checks that the u32 key is actually the first field. The doc comment (src/sort.rs:52-56) claims this holds for `T = (u32, V)` "in Rust's default repr (u32 at offset 0, aligned)", but `#[repr(Rust)]` field order (including tuples) is unspecified by the language and is only empirically stable, not guaranteed. `src/gpu/agx.rs:161` uses exactly this pattern with `FVec<'_, (u32, u64)>`, mixing a 4-byte-aligned key with an 8-byte-aligned payload field.

**Failure scenario:** I verified with a standalone rustc program that today's compiler keeps `(u32, u64)`'s u32 field at offset 0 despite u64 having larger alignment (rustc's optimal-layout pass only reorders when it would shrink the total size, and here both orders produce the same 16-byte layout, so it doesn't bother) — so the current binary is correct. But nothing pins this: a future rustc layout-algorithm change, or a future call site adding a tuple where reordering *would* save space (e.g. mixing more differently-sized fields), would silently place a different field at offset 0. `sort_mono`'s `key()` closure would then read the wrong 4 bytes as the sort key with no compile error and no panic — just a process list quietly sorted/keyed by the wrong values (e.g. AGX per-pid GPU-memory entries merged/attributed to the wrong pid in `freeze_map`), which is exactly the kind of silently-wrong-output class this audit prioritizes. A `#[repr(C)]` wrapper struct or a `const { assert!(core::mem::offset_of!(T, 0-field) == 0) }`-style check (once stable for tuples) would make the precondition compiler-enforced instead of convention-enforced.


## Design takes (curated)

### [HIGH] Frame::replace has zero production callers; replace2 already subsumes it

*area: src/arena.rs (Frame::replace, ~703-767, + 6 tests ~3082-3200)*

Verified: grepping `.replace(` outside `replace2`/`str::replace` across src/ turns up only arena.rs's own test module (6 tests). main.rs::run only ever calls replace2 for the gpu_prev/prev cross-tick rotation. replace2 already supports the single-span case (a ZST second span, as Linux's gpu_prev already demonstrates), so replace is redundant machinery: ~80 lines of copy_down/trace bookkeeping plus ~125 lines of dedicated tests testing something replace2 also tests.

**Suggestion:** Delete Frame::replace and its 6 tests; route any future single-span-rotate need through replace2 with a ZST second span. If there's a concrete reason to keep both, leave a comment so a future pruning pass doesn't re-derive this from scratch.

**Bonsai note:** Source-complexity prune, likely LTO already strips the bytes (verify with nm before/after) - the win is fewer lines and fewer redundant tests to maintain, exactly the pruning-not-grafting spirit.

### [HIGH] The installed seccomp filter is never exercised by a real tick loop in any CI job

*area: src/sandbox.rs vs .github/workflows/linux-*.yml*

Verified: both linux-x86.yml and linux-arm.yml only run --check, which exits via exit_group(0) in parse_args before run() (and therefore before sandbox::install() at main.rs:567) is ever reached. mac-arm.yml does run --once (which reaches sandbox::install), but sandbox.rs is Linux-only and compiles to nothing there. So no CI job on any platform ever runs a real steady-state tick with the seccomp filter installed. A future change that adds one syscall to the hot path compiles clean, passes every unit test, and then SIGKILLs on first real use with zero CI signal.

**Suggestion:** Add a Linux CI step that runs the real min binary for one real tick under the installed filter (--once) and asserts a clean exit (0), not a kill-by-signal exit code.

**Bonsai note:** Zero production bytes (CI-only); protects the single scariest failure mode of the sandbox work (silent SIGKILL) with a test that costs nothing to ship.

*area: src/main.rs:655-658 (comment on the per-tick sort call)*

*area: CLAUDE.md:72, src/main.rs:607, src/arena.rs:221 vs src/gpu/rm.rs*

### [HIGH] The file most responsible for wrong-output bugs (CPU%, tree layout, filtering, truncation) has zero unit tests

*area: src/main.rs (whole file, 1899 lines, zero tests)*

Verified grep -c '#[test]' src/main.rs is 0. This module owns exactly the correctness surface flagged as priority in review: Packed bit-packing, tree_layout/filter_with_children, render_tree's child-budget math, truncate(). All pure/deterministic and fixture-able with synthetic ProcInfo arrays. Every other module of comparable complexity has a test module (arena.rs 82 tests, sandbox.rs 23, mac_sys.rs 18); main.rs is the outlier, and it isn't a structural gap - bin-crate #[cfg(test)] mod tests needs no lib.rs plumbing. **Suggestion:** Add #[cfg(test)] mod tests to main.rs covering: Packed pack/unpack round-trip at the age_secs/VISIBLE_BIT boundary; truncate() at max=0..3 and exact-fit; filter_with_children on a synthetic forest (hidden-parent child, orphaned pid, cyclic ppid); render_tree's child_budget rounding. Zero production bytes since these are cfg(test)-only.

**Bonsai note:** Pure test-only addition - no production bytes, and it's the single highest-leverage correctness net missing from the codebase given main.rs's size and role.

### [HIGH] Kernel-ABI struct layouts documented by comment (e.g. '72 bytes') are never asserted against size_of

*area: src/gpu/rm.rs - NvIoctlRmApiVersion/NvIoctlCardInfo/NvPerfmonUtilParams/NvGetPidsParams/NvGetPidInfoParams*

Verified: comments state expected sizes from primary sources but no test asserts size_of::<T>() against them, unlike sandbox.rs's own kernel_struct_layout test which pins SockFilter's size/align against the real kernel ABI for exactly this reason. A reordered or mis-sized #[repr(C)] field here is still trivially Zeroable-sound (all-zero stays valid) but silently truncates/misaligns the ioctl payload - wrong or garbage GPU stats with no compile or runtime signal.

**Suggestion:** Add one #[test] fn struct_sizes_match_driver_headers() in gpu/rm.rs asserting size_of::<T>() for each of the five structs against the literal already in each comment.

**Bonsai note:** Cfg(test)-only, zero production bytes; turns five drive-by comments into load-bearing regression checks using a pattern the codebase already trusts (sandbox.rs's identical test).

### [MEDIUM] Stale #[allow(dead_code)] + 'Phase-N plumbing' comments on functions gpu/agx.rs calls unconditionally every tick

*area: src/mac_sys.rs (io_master_port, mach_port_deallocate, AGX_MATCHING_BLOB, io_service_get_matching_services_bin, io_iterator_next, io_registry_entry_get_child_iterator, io_registry_entry_get_properties_bin, OolBuffer, vm_deallocate)*

Verified: every one of these carries #[allow(dead_code)] and a 'Phase-N plumbing, first caller lands in Phase M' comment, but gpu/agx.rs's count_agx_devices and populate() call all of them unconditionally on the always-compiled macOS production path (confirmed by direct grep of agx.rs call sites). **Suggestion:** Remove the #[allow(dead_code)] attributes and replace the 'Phase-N plumbing' lines with what the function does today (most already have a good doc comment above the stale line).

**Bonsai note:** Comment/attribute-only, zero bytes; downgraded from high only because it's confusing-but-harmless rather than actively wrong like the CLAUDE.md/main.rs comment findings.

### [MEDIUM] row_color duplicates its entire RSS-color formula across a cfg split just to dodge unused_mut

*area: src/main.rs:1869-1895 (row_color)*

Verified: the two branches are byte-for-byte identical expressions (rss_kib as u64 * 255 / (4u64 << 20)).min(255) as u8, differing only in the mut keyword (macOS never reassigns r later since there's no per-process GPU-memory column on Apple Silicon). If the RSS-to-red scaling constant ever changes, both copies must be updated in lockstep with no compiler signal if one is missed.

**Suggestion:** Declare let mut r = ... once, unconditionally, and suppress the harmless mac-only unused_mut with #[cfg_attr(target_os = "macos", allow(unused_mut))] instead of duplicating the expression.

**Bonsai note:** Byte-neutral (LTO folds both branches to the same code today) but removes a real duplication hazard - one formula, one place to change it.

### [MEDIUM] The procs[i]/next[i] lockstep invariant CLAUDE.md flags is enforced only by comment, independently on both platforms

*area: src/main.rs collect_procs (Linux ~1289-1364, macOS ~1072-1086) vs procs[i]/next[i] pairing*

Verified the 'push placeholder first, overwrite later' pattern and its lockstep comments exist on both platforms as described. Nothing but a comment enforces that every push into procs pairs with exactly one push into next at the same index; an early continue inserted before the next.push() on either platform would silently desync the arrays with no compile or runtime signal, and filter_with_children's visibility-setting would then flip the wrong pid. gpu/mod.rs's GpuInfo::usage (single cfg-gated function, one call site) is a good contrasting precedent already in the codebase for how to unify per-platform semantics behind one signature instead of two hand-duplicated loops.

**Suggestion:** Introduce a small paired-push helper (or derive next from procs in one pass at the end of collect_procs) so there is exactly one place the pairing can break instead of two independently-maintained loops.

**Bonsai note:** A small helper function is a few bytes at most (likely inlined away under LTO) in exchange for closing a real silent-corruption risk in a CLAUDE.md-flagged invariant.

### [MEDIUM] The one test that checks GPU stats are numerically correct has a 100% skip rate in every CI run

*area: src/gpu/rm.rs rm_matches_nvml and friends vs CI*

rm_matches_nvml and its siblings are cfg_attr(not(has_gpu), ignore), gated on build.rs finding /dev/nvidiactl. All three CI workflows run on GH-hosted runners with no NVIDIA hardware and never pass -- --ignored, so has_gpu is never set and this suite never executes in CI, indistinguishable from having no test at all from CI's perspective, on a subsystem the review brief ranks priority-2.

**Suggestion:** Add a hardware-independent fixture test: capture one real RM ioctl reply buffer as a static byte array and run it through the parsing/aggregation code path with an expected-output assertion - much cheaper than standing up a self-hosted GPU runner and covers the part most likely to regress (parsing/math, not the ioctl call itself).

**Bonsai note:** Test-only, zero production bytes; doesn't fully replace the real-hardware test but converts 'never runs' into 'always runs deterministically' for the higher-risk parsing logic.

*area: mac-arm.yml Mach-O structure checks vs tests/stack_frames.rs (Linux)*

*area: src/main.rs (whole file, 1899 lines)*

Verified the file holds all of: platform collect_procs, classification heuristics (is_noise/is_lean_*/find_*), tree layout (build_pid_to_idx/build_children/tree_walk), rendering (emit_proc_row/render_tree/Format*), and color math - five orthogonal concerns in one 1899-line file, while every other subsystem (twrite, bytes, sort, map, tty, sandbox, gpu/*) already has its own file. ### [MEDIUM] 'u32 key at offset 0' is checked for size/alignment but not identity - a convention, not a type guarantee

*area: src/sort.rs sort_by_u32_key + src/map.rs freeze_map/freeze_set*

Verified sort_by_u32_key's const-asserts only check size_of%4==0 and align_of>=4, which cannot prove the u32 at offset 0 is actually the intended sort key (pid, in ProcInfo's case, documented only in a comment). A future field reorder on a #[repr(C)] type passed to this function would pass the asserts and silently sort by the wrong field, manifesting as a misbehaving process tree with no compiler signal.

**Suggestion:** A zero-cost marker trait callers opt into explicitly (unsafe trait KeyAtOffset0, implemented per type) turns the requirement into something grep-able and gives each type one place to attach a const { assert!(offset_of!(T, field) == 0) } compile-time proof, replacing what today is only a comment.

**Bonsai note:** A marker trait is a zero-cost abstraction (no vtable, no runtime check) - free insurance against a genuinely silent correctness bug class, in the spirit of the codebase's existing Zeroable marker trait.

### [MEDIUM] syscall::write_all is a single write(2) with no retry, but its name and the one real caller's usage pattern suggest otherwise

*area: src/syscall.rs:505-518 write_all vs src/tty.rs:149-156 write_stdout*

**Suggestion:** Rename to something that doesn't imply retry-to-completion (e.g. write_once), and update the now-misleading 'use write directly for partial-write loops' guidance since write_stdout demonstrates looping over the safe wrapper works fine.

**Bonsai note:** Rename only, zero bytes - pure naming-collision fix that removes a real chance of a future reader misjudging retry behavior.
